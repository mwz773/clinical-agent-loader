Synthea FHIR JSON
    ↓
S3 source bucket
    ↓
load_fhir.py
    ↓
RDS PostgreSQL
    ↓
build_context.py
    ↓
bounded context JSON
    ↓
run_brief.py / Bedrock
    ↓
validated brief
    ↓
processed S3 bucket + RDS audit tables


- S3 raw/source bucket stores original Synthea FHIR Bundle JSON files.
    This is your immutable source data.

- load_fhir.py downloads each FHIR Bundle from S3, parses resources such
  as Patient, Encounter, Condition, MedicationRequest, and DiagnosticReport,
then writes them into normalized PostgreSQL tables on RDS.

- RDS PostgreSQL is the structured clinical-history layer. It stores:
        patient demographics
        encounters
        conditions
        medications
        observations
        decoded clinical notes
        clinical events


- build_context.py queries RDS for one selected patient. It creates a limited, relevant
  context containing the current and prior notes, verified changes, active records, and a selected multi-year timeline.
  It does not modify the database.


- run_brief.py sends that bounded context to Bedrock. Bedrock returns a structured brief;
  the script rejects unsupported citations, then saves a validated artifact to the processed
  S3 bucket and records the run, brief, and cited evidence in RDS.


  Clinical Agent Data Model
===========================

The database has two connected layers:

1. Clinical-history data loaded from Synthea FHIR Bundles.
2. AI brief and audit data generated by the care-coordination workflow.


Relationship map
----------------

patients
  ├── encounters
  │     ├── conditions
  │     ├── medications
  │     ├── observations
  │     └── clinical_notes
  ├── conditions
  ├── medications
  ├── observations
  ├── clinical_notes
  ├── clinical_events
  └── agent_runs
          ├── follow_up_briefs
          └── brief_evidence


Tables and keys
---------------

patients
  Primary key: patient_id
  The root record for one synthetic patient.

encounters
  Primary key: encounter_id
  Foreign key: patient_id -> patients.patient_id
  Represents a visit or other patient encounter.

conditions
  Primary key: condition_id
  Foreign keys:
    patient_id -> patients.patient_id
    encounter_id -> encounters.encounter_id (optional)
  Represents a FHIR Condition record.

medications
  Primary key: medication_request_id
  Foreign keys:
    patient_id -> patients.patient_id
    encounter_id -> encounters.encounter_id (optional)
  Represents a FHIR MedicationRequest record.

observations
  Primary key: observation_id
  Foreign keys:
    patient_id -> patients.patient_id
    encounter_id -> encounters.encounter_id (optional)
  Represents measurements, results, and other FHIR Observation records.

clinical_notes
  Primary key: note_id
  Foreign keys:
    patient_id -> patients.patient_id
    encounter_id -> encounters.encounter_id (optional)
  Stores decoded note text from the FHIR DiagnosticReport presented-form data.

clinical_events
  Primary key: event_id
  Foreign keys:
    patient_id -> patients.patient_id
    encounter_id -> encounters.encounter_id (optional)
  Stores selected longitudinal FHIR resources, including DiagnosticReport,
  Procedure, CarePlan, ServiceRequest, Appointment, and Goal.

ingestion_files
  Primary key: source_s3_key
  Tracks every source FHIR Bundle in S3, including ingestion status, resource
  counts, an optional patient_id, and any loading error.

agent_runs
  Primary key: run_id
  Foreign keys:
    patient_id -> patients.patient_id
    note_id -> clinical_notes.note_id
  Stores one Bedrock brief-generation attempt, including model ID, latency,
  token usage, and status.

follow_up_briefs
  Primary key and foreign key: run_id -> agent_runs.run_id
  Stores one validated structured brief for a successful agent run.

brief_evidence
  Composite primary key: run_id, resource_type, resource_id
  Foreign key: run_id -> agent_runs.run_id
  Stores each FHIR resource cited as evidence by a generated brief, together
  with the source S3 key where that record originated.


Important connection keys
-------------------------

patient_id
  Connects every clinical-history record to one patient.

encounter_id
  Optionally connects a note, condition, medication, observation, or event to
  a specific patient encounter.

run_id
  Connects one Bedrock invocation to its persisted brief and cited evidence.


Audit trail
-----------

A reviewer can trace a generated review item back to its underlying data:

Patient
  -> current clinical note
  -> agent_runs.run_id
  -> follow_up_briefs
  -> brief_evidence.resource_id
  -> original FHIR resource in the source S3 Bundle

This traceability is enforced by brief validation: the model can cite only
resource IDs supplied in its bounded patient context.
